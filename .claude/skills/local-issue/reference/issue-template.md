## Issue作成ルール
### フィールド
- `id` : 2桁の連番。派生Issueは `08a`, `08b` 形式（元Issueをcloseして新規作成）
- `対象` : 変更・新規作成するファイルをすべて列挙する。新規は (新規) を付記
- `depends` : 先にマージされている必要がある Issue の id（同じ `issues/` の中）。`i` はその Issue が main の `done/` に現れるまで、この Issue を実装の候補に出さない。同じファイルの同じ箇所や連番を、動いている実行者と取り合う場合もそのブランチの Issue を書く
- `内容` : 目的と概要のみ。実装仕様は下のセクションに書く
- `対象外` : 目的に近いが今回はやらないことを挙げる。実行者は気づいた改善があってもここへ手を広げない。無ければ `なし` と明示する（省略すると、考えて無いのか書き忘れたのか区別できない）
- `仮定` : 要件の曖昧さのうち、user に質問せず相談者が判断で埋めたものを挙げる。質問しなかった判断はここ以外に残らない。無ければ `なし` と明示する
- `確認` : 実行者が提出前に行い、確認者（`issue-verifier`）が判定の基準にする確認。このリポの CLAUDE.md の検証手段を参照して埋める。例: lib変更時は影響callerをすべて列挙・修正済みであること。画面に出る挙動は、どの画面に何がどの値で出るかまで書く。ヘッドレスのブラウザで再現できない操作（画面全体の共有、OS の権限や共有のダイアログ、印刷、通知）は、ブラウザの API を差し替えて確かめられる形（渡す引数、失敗したときの表示）で書き、本物の操作は `人が見るもの` に回す
- `人が見るもの` : 書いて渡せない判断（画面の使い心地）と、エージェントが実行できない確認（rebuild・deploy・実機）。挙動の照合はここに書かない。無ければ `なし` と明示する
### ライフサイクル
- `status: draft` → 設計中
- `status: open`  → `i` で実装の候補に出る。**open は user が保証節・`対象外`・`仮定` を承認済みであることを含む**
- `status: close` → 完了済み（user の OK 後に実行者が `done/` へ移して更新し、PR に載せる）
PR を出す前の確認で出た問題は、実行者のセッションで直す。新しい Issue にしない。
マージ後に問題が出た場合は、元の Issue を再 open せず、`{id}a` として新しい Issue を作成する。
### 保証節
- 保証は自然言語で書く。テストコードやテストファイル名の指定は補足であり、主体は振る舞いの宣言
- user は draft→open の承認で保証節を必ず読み、削る・足す・直す（保証節は user 承認済みであることが open の意味に含まれる）
- テストを伴わない変更（ドキュメントのみ・cleanup 等）は `保証: なし（理由）` と明示する。無記載は不可
- リポに保証台帳 `docs/guarantees.md` がある場合、「維持する保証」は台帳から引く。台帳の記載に変更が出る場合（新保証・変更・廃止）は台帳を対象ファイルに含める
- 「廃止する保証」に挙げたものは、台帳があれば台帳からも外し、対応するテストの扱い（削除・書き換え）を詳細セクションに書く
### 粒度
分ける目的は2つある。約束を1つずつ承認して確かめることと、並行して進めることである。分けるほど確認者の判定・user の確認・PR の手間が本数分かかるので、どちらの得にもならない分け方はしない。対象ファイルの数では決めない。ファイルの数は確かめる量とも約束の数とも比例しない。

次の4つを上から順に当てる。

1. **上限を超えたら分ける。** 次のいずれかに当たったら分ける
   - 要件から起こした `確認` の項目が15件を超える。実装の往復と確認者の判定が項目の数に比例して延びる。基準を数にするのは、超えたかどうかの解釈が起票のたびに揺れないようにするためである。静的チェック・既存テストの維持・文書の更新の行は数えない。ほとんどの Issue に付く行なので、数えると小さい Issue 同士もまとめられなくなる
   - 変える画面が2つ以上ある。ページ内の切り替えは数えない。使い心地の確認と直しの往復が画面ごとに増える
   - 確認手段が2種類以上ある（例: サーバ上での実行確認と、ブラウザでの目視確認）。画面に出る要件の API のテストと画面での確認は、1種類と数える
2. **並行して動かせないものはまとめる。** 次のどちらかに当たり、まとめても 1 に当たらないなら1本にする。分けても1本ずつ順にしか進まず、後の Issue が前の Issue の変えたところを直し直すことになる
   - 動いている実行者か、同時に書く Issue と、同じファイルの同じ箇所を書き換える。箇所は関数や節の単位で見る
   - 片方の結果を見てからでないと、もう片方を作れない。バックエンドとフロントエンドもこれで決める。画面に出る要件は API と画面で分けない

   まとめると 1 に当たるなら分け、後の Issue の `depends:` に先の Issue を書く
3. **小さいものはまとめる。** 要件から起こした `確認` の項目が3件以下の Issue は、同じ対象か同じ画面を変える Issue とまとめても 1 に当たらないなら、1本にする。小さい Issue では本数分かかる手間が実装より重くなる。まとめる相手が無ければ、そのまま1本にする
4. **それ以外は、保証台帳の区切り1つで切る。** 保証台帳 `docs/guarantees.md` を持つリポでは、1本の Issue が触れる区切り（台帳のテストファイルごとの `###` の節）を1つにする。新しく起こすか、既存の1つに足す。作業の量ではなく約束の単位で切るためである。台帳の無いリポと `保証: なし` の Issue はこの基準の外にある

2 か 3 でまとめた Issue の保証節は、新たに宣言する保証を区切りごとに分けて書く。2 か 3 に当たるのにまとめないと決めたら、当たった基準と理由を報告に添える。
### 詳細セクション
- `内容` に収まらない仕様は `---` 以降に自由に展開する
- ファイルごとに見出しを立てる
- 実装順序が重要な場合は末尾に明記する
