相談者として規則ファイル（CLAUDE.md群・docs-agents・自作Skill の trigger 記述）の棚卸しを行う。`consolidate-memory` Skill（現状把握→統合→索引整理の3段階、`MEMORY.md` を索引として都度更新する構造）と `guarantee-audit` Skill（指摘提示→user 裁可→反映の進行）の型を、対象を「メモリ」から「規則」に変えて踏襲する。**プロダクトコード（各リポの src/ 等）は書かない**。書いてよいのは対象節に挙げた規則ファイルと索引ファイル `~/dotfiles/.claude/RULES.md` のみ。

## 背景

CLAUDE.md・Skill・memory はいずれも「user が書いた規則を AI が読む」構造であり、規則同士の矛盾を検出する仕組みを内蔵していない。規則ファイルは増え続けており、矛盾や陳腐化した規則はいずれ AI の挙動を不安定にする。本 Skill はその棚卸しを場当たりではなく**定期的に**（`schedule` / `loop` からの起動を想定）繰り返すための仕組みであり、毎回全ファイルを読み直すコストを避けるために索引ファイルを介する。索引を持たない設計では実行のたびに対象ファイル全部を読むことになり、定期実行のコストが線形に積み上がる。

## 対象

- `~/.claude/CLAUDE.md`（グローバル）
- 各リポの `CLAUDE.md`（呼び出し元リポ、または user が指定したリポ）
- `~/dotfiles/docs-agents/*.md`
- `~/dotfiles/.claude/skills/*/SKILL.md` のうち、frontmatter `description` が**日本語で書かれているもの**

最後の条件により、Cloudflare 等ベンダー技術リファレンス系Skill（`cloudflare` / `wrangler` / `agents-sdk` / `durable-objects` / `sandbox-sdk` / `web-perf` / `workers-best-practices` 等、description が英語）と Anthropic 標準搭載Skill（`anthropic-skills:*` prefix、`docx` / `pdf` / `pptx` / `xlsx` / `schedule` / `morning` / `setup-cowork` / `skill-creator` / `consolidate-memory` 等）を除外する。これらは user 自身が書いた「規則」ではなく外部ドキュメントの写しか Claude Code 標準機能であり、CLAUDE.md との矛盾を検出する対象にする意味がない。**この判定は実行時に frontmatter を機械的に見て行い、固定の除外リストは保守しない**（Skill の増減に自動で追従させるため）。

**`docs-agents` は基準の実体であり、本 Skill によって Skill へ昇格させない。**本 Skill は docs-agents を読みに行く側であり、既存の `repo-standardize` 等が docs-agents を参照する構造は変更しない。

## 索引 (`~/dotfiles/.claude/RULES.md`)

`MEMORY.md` と同じ「索引であって規則の実体ではない」位置づけのファイル。対象ファイル1件につき次の1行のみを書く。

`- **{ファイルパス}** — {一言要約（見出し・扱う対象を示す1文。規則の中身を書き写さない）}。相互参照: {依存/被依存の対象ファイル。例: `docs-agents/issue-driven-workflow.md` は `docs-agents/test-policy.md` の基準を前提にしている、`new-issue/SKILL.md` は CLAUDE.md の「相談者と実行者を分ける」節を実装している、等。無ければ省略}。棚卸し: {commit hash} {日付}`

**書かないもの**（この1行フォーマット以外の追記は行わない）:
- 規則の内容そのもの。要約は「何を扱うファイルか」を示すだけに留め、規則の条文・値・判断基準を転記しない
- 棚卸しの経緯・矛盾の指摘内容・議論ログ。「今回反映した指摘」のような変更ログ節は作らない（経緯は git commit メッセージ、または実行時のチャットに残ればよく、索引に恒久保存する対象ではない）
- 「対象」節で定義された範囲外のファイル。一時的に他リポを調査した場合も、そのリポを索引に恒久登録しない（次回の定期実行が自然に触れない対象は陳腐化するだけ）

存在しない場合はフェーズ1で対象節の全ファイルを精読してブートストラップし、フェーズ3で書き出す。存在する場合はフェーズ1で全文を読み直さず、この索引を起点に前回からの変更分だけを扱う。フェーズ3での更新は既存行への**上書き**であり、追記ではない。

## フェーズ1: 現状把握

1. `~/dotfiles/.claude/RULES.md` を読む。無ければ対象節の全ファイルを精読する（索引が無い＝初回実行であり、索引のブートストラップはフェーズ3で行う。ここでは読むだけで先に進まない）。
2. 索引がある場合、対象ファイルの更新日時（または git log）を索引の記録と突き合わせ、前回棚卸し後に変更があったファイルを特定する。未変更のファイルは索引の要約・相互参照をそのまま根拠として使う（内容を疑う具体的な理由があれば個別に読み直してよい）
3. 対象ファイル全件（索引が無い場合は全対象。索引がある場合は変更ファイルと、索引上でそれらと相互参照関係にあるファイル）について、次の3観点で乖離を洗い出す
   1. docs-agents 内部の相互矛盾（例: `test-policy.md` と `issue-driven-workflow.md` で基準がずれる）
   2. CLAUDE.md（グローバル/リポ別）と docs-agents の乖離（CLAUDE.md にしか書かれていない規則が docs-agents の更新で置き去りになっていないか）
   3. Skill の trigger 記述（`description:`）と本文の乖離（規則が変わったのに Skill の説明が古いまま残っていないか）

**対象ファイルを全て読み終え、3の洗い出しが完了するまで、見つけた乖離を1件ずつ個別にuserへ提示・確認しない。**見つけ次第の報告・裁可要求はせず、フェーズ1完了後にフェーズ2でまとめて提示する。フェーズ3のインデックス・ブートストラップは、フェーズ2の裁可・反映がすべて終わったあとに行う。

## フェーズ2: 統合

1. 乖離ごとに、どちらが正（基準の実体）かを判定する。同じ規則が複数箇所に重複しているだけなら、正本を残し他方を「正本を参照する」形に薄くする方向で提案を組み立てる（内容そのものを複製しない）
2. 指摘一覧をチャットに提示する（ファイルに書き出さない）。各指摘は「対象ファイル:該当箇所 → 矛盾/陳腐化の内容 → 提案」の形で1件ずつ書く
3. 指摘ごとに user の明示的な裁可（YES/NO/修正）を得てから該当ファイルを編集する。**auto memory 節のルールと同じ扱いで、内容そのものへの同意を毎回得る**（複数の指摘をまとめて一括承認する運用にしない）。user は対話で指示してもよいし、ファイルを直接編集してもよい
4. 裁可された指摘のみを反映する。編集は該当箇所の最小差分に留め、裁可を経ていない周辺の言い回しには手を入れない

## フェーズ3: 索引整理

1. 反映後、編集した Skill の frontmatter `description` が本文と再び一致しているかを確認する
2. CLAUDE.md 側の `@import` や docs-agents への参照が、実体のファイル名・見出しと一致しているかを確認する
3. `~/dotfiles/.claude/RULES.md` を更新する。今回精読・編集した対象ファイルの要約・相互参照・棚卸し時点の更新日時を書き直す。索引が存在しなかった場合はここで対象節の全ファイル分を新規に書き出す
4. ずれが残っていればフェーズ2に戻る。無ければ変更ファイル一覧と反映済み指摘の要約を報告して終了する

## 定期実行

本 Skill は `schedule` または `loop` からの定期起動（週次程度を想定）を前提に設計している。索引方式により2回目以降の実行は変更差分のみを扱うため、頻度を上げても現状把握のコストが線形に増えない。定期実行そのものの設定は本 Skill の責務外であり、user が `schedule` Skill 経由で別途組む。

## 制約

- プロダクトコード（各リポの src/ 等）は書かない
- 裁可を経ていない指摘は反映しない。指摘が複数ある場合、要約や「まとめてOK」だけで済ませず、内容ごとの同意を確認する
- コミット・push はしない。変更はワーキングツリーに残し、user がレビューしてコミットする
- `~/dotfiles/.claude/RULES.md` は索引であり規則の実体ではない。ポインタ・要約・相互参照・更新日時のみを書き、規則の内容そのものを複製しない
