相談者として規則ファイル（CLAUDE.md群・docs-agents・自作Skill の trigger 記述）の棚卸しを行う。`guarantee-audit` Skill（指摘提示→user 裁可→反映の進行）の型を、対象を「メモリ」から「規則」に変えて踏襲する。**プロダクトコード（各リポの src/ 等）は書かない**。書いてよいのは対象節に挙げた規則ファイルと索引ファイル `.claude/RULES.md` のみ。

## 背景

CLAUDE.md・Skill・memory はいずれも「user が書いた規則を AI が読む」構造であり、規則同士の矛盾を検出する仕組みを内蔵していない。規則ファイルは増え続けており、矛盾や陳腐化した規則はいずれ AI の挙動を不安定にする。本 Skill はその棚卸しを場当たりではなく**定期的に**（`schedule` / `loop` からの起動を想定）繰り返すための仕組みであり、毎回全ファイルを読み直すコストを避けるために索引ファイルを介する。索引を持たない設計では実行のたびに対象ファイル全部を読むことになり、定期実行のコストが線形に積み上がる。

## 対象

- `~/.claude/CLAUDE.md`（グローバル）
- 各リポの `CLAUDE.md`（呼び出し元リポ、または user が指定したリポ）
- `docs-agents/*.md`
- `.claude/skills/*/SKILL.md` のうち、frontmatter `description` が**日本語で書かれているもの**
- `.claude/settings.json` と `.claude/hooks/*.sh`（層1）

層1 を含めるのは、そこが「ガイドが規定していて、実体が別ファイルにある」唯一の層だからである。`harness-guide.md` は deny の共通項目・フック一覧・attribution を規定しているが、規定を満たしているかは settings.json と `hooks/` を読まない限り分からない。文書同士の突き合わせだけでは、規定と実体の乖離は永久に検出されない。

**層1 だけは実体が正で、ガイドが従である。** deny を1本増やす・減らすといった判断は運用の中で下されており、それを追認していないガイドの側が古い。他の対象と違い、食い違ったら実体に合わせてガイドを直す。

最後の条件により、Cloudflare 等ベンダー技術リファレンス系Skill（`cloudflare` / `wrangler` / `agents-sdk` / `durable-objects` / `sandbox-sdk` / `web-perf` / `workers-best-practices` 等、description が英語）と Anthropic 標準搭載Skill（`anthropic-skills:*` prefix、`docx` / `pdf` / `pptx` / `xlsx` / `schedule` / `morning` / `setup-cowork` / `skill-creator` / `consolidate-memory` 等）を除外する。これらは user 自身が書いた「規則」ではなく外部ドキュメントの写しか Claude Code 標準機能であり、CLAUDE.md との矛盾を検出する対象にする意味がない。**この判定は実行時に frontmatter を機械的に見て行い、固定の除外リストは保守しない**（Skill の増減に自動で追従させるため）。

**`docs-agents` は基準の実体であり、本 Skill によって Skill へ昇格させない。**本 Skill は docs-agents を読みに行く側であり、既存の `repo-standardize` 等が docs-agents を参照する構造は変更しない。

## 索引 (`.claude/RULES.md`)

索引であって規則の実体ではない位置づけのファイル。先頭にアンカー1行を置き、以降は対象ファイル1件につき次の1行のみを書く。

`最終棚卸し: dotfiles {commit} — {日付} — モデル {実行時のモデル ID}`

モデル ID を書くのは、規則の陳腐化がファイルの変更だけでなく**モデルの世代交代でも起きる**ため。古いモデルの弱点を補うために書いた規則は、その弱点が消えた時点で制約にしかならないが、規則ファイル自体は1文字も変わらないのでハッシュの差分には現れない。世代交代を捉える差分はここにしか置けない。

記録されたモデル ID が実行時のモデルとメジャー世代で違うとき、ハッシュが一致していて読まないはずのファイルも含め、**モデル特化の記述だけを対象に全件を1周見る**（判定はフェーズ1の観点4）。同じ世代で回している間はこの掃引を行わない。

アンカーは**棚卸し自身が記録する**。本リポへの push を進捗マーカーに使わない。ここへの push は `issue-finish` の PR マージ・Dependabot・単発修正でも起きるため、棚卸しをしていない push でアンカーが進み、その手前で非公開側に入った規則変更を読まずに素通りする。

`- **{ファイルパス}** — {一言要約（見出し・扱う対象を示す1文。規則の中身を書き写さない）}。相互参照: {依存/被依存の対象ファイル。例: `docs-agents/issue-driven-workflow.md` は `docs-agents/test-policy.md` の基準を前提にしている、`new-issue/SKILL.md` は CLAUDE.md の「相談者と実行者を分ける」節を実装している、等。無ければ省略}。正本: {private / public / 双方向。片側にしか実体が無いファイルでは省略}。棚卸し: {内容ハッシュ} {日付}`

**`棚卸し:` の内容ハッシュは「その内容を精読した」という宣言である。** `git hash-object {file}` の先頭8桁を書く。commit hash ではなく内容そのもののハッシュにするのは、棚卸しで直したファイルを user がコミットした瞬間に「変更あり」へ落ちて次回また読み直す、という手戻りを避けるため。中身が変わったときだけ再読になる。別の理由でその行に触った場合でも、精読していないなら更新しない。フォーマットの外に「今回は深読みしていない」と散文で注記して埋め合わせることもしない（次回の実行がその注記を読み落とし、精読済みとして素通りする）。

アンカーは**何が変わったかを差分で取る**ために、ハッシュは**どこまで読んだかを行ごとに宣言する**ために使う。片方には寄せられない。アンカーだけでは未コミットの変更（dotfiles は日常的に dirty）が候補から落ち、途中で切れた回に「12件中5件だけ精読した」を表現できない。

`正本:` は、非公開の dotfiles と本リポの両方に実体があるファイルにだけ書く。どちらを直せば他方が従うのかが宣言されていないと、乖離が双方向に育ち、検出が後手に回る。

**書かないもの**（この1行フォーマットと後述の「裁可済みの差分」節以外の追記は行わない）:
- 規則の内容そのもの。要約は「何を扱うファイルか」を示すだけに留め、規則の条文・値・判断基準を転記しない
- 棚卸しの経緯・矛盾の指摘内容・議論ログ。「今回反映した指摘」のような変更ログ節は作らない（経緯は git commit メッセージ、または実行時のチャットに残ればよく、索引に恒久保存する対象ではない）
- 「対象」節で定義された範囲外のファイル。一時的に他リポを調査した場合も、そのリポを索引に恒久登録しない（次回の定期実行が自然に触れない対象は陳腐化するだけ）

### 裁可済みの差分（再検討しない）

非公開側と本リポで内容が違うが、それが user の裁可を経た意図的な差分であるものを1行ずつ記録する。**次回以降の実行は、この節に載っている差分を指摘として再提起しない。** 高頻度で回す以上、決着済みの差分を毎回持ち出すのが最大の手戻りになる。

`- **{対象A} ↔ {対象B}** — {何が違うか（1文）}。{裁可日}`

書くのは対象と差分の一文と日付だけで、理由の議論は書かない。差分が解消された（内容が同一になった）行は削除する。

## フェーズ0: 対象の突き合わせ（読む前に機械的に行う）

規則ファイルを1つも読まずに、対象の集合と索引の行を突き合わせる。

1. 対象節の定義に従って対象ファイルを列挙する（`docs-agents/*.md`、`description` が日本語の `SKILL.md`、CLAUDE.md 群、`settings.json` と `hooks/*.sh`）
2. アンカーからの候補を1コマンドで取る。

   ```sh
   git log {anchor}..HEAD --name-only --pretty=format: | sort -u
   git status --porcelain          # 未コミット分を足す
   ```

3. 各ファイルの内容ハッシュを取る（`git hash-object {file} | cut -c1-8`。作業ツリーの実体で判定できる）
4. 候補と索引の行を突き合わせ、次の3つに仕分ける

| バケツ | 判定 | 扱い |
|---|---|---|
| **未登録** | 対象にあるが索引に行が無い | 全文を精読し、フェーズ3で行を作る |
| **消滅** | 索引に行があるが実体が無い | 読まずにフェーズ3で行を削除する |
| **変更あり** | 内容ハッシュが索引の `棚卸し:` と違う | フェーズ1で差分を読む |

残り（内容ハッシュが索引の記録と一致するファイル）は**読まない**。索引の要約・相互参照をそのまま根拠に使う。内容を疑う具体的な理由があるときだけ個別に読み直す。

**仕分けの正はハッシュであってコミット範囲ではない。** 2 は候補を安く絞るための道具で、範囲に出たがハッシュが一致するファイル（触って戻した等）は「変更なし」として落とす。逆にアンカーが古い・履歴が書き換わった等でコミット範囲が信用できないときは、2 を飛ばして対象全件のハッシュを取る。

## フェーズ1: 現状把握

1. フェーズ0で「未登録」「変更あり」に入ったファイルと、索引上でそれらと相互参照関係にあるファイルだけを読む。**「変更あり」は全文ではなく差分を読む**（`git diff {anchor}..HEAD -- {file}`。未コミット分は `git diff` を重ねる）。前回精読した内容は索引の要約が保証しているので、そこへ差分を重ねれば足りる。差分だけでは前後の文脈が判断できないときに限り、その節を読み足す。索引そのものが無い場合は対象節の全ファイルを精読する（索引が無い＝初回実行であり、索引のブートストラップはフェーズ3で行う。ここでは読むだけで先に進まない）

   **読む対象が5ファイルを超えるとき、この読み込みは読み取り専用の探索 subagent に投げる。**（`Explore` 等。初回実行と、観点4のモデル世代の掃引は必ず該当する。）本体の文面すべてが親のコンテキストに載ると、裁可の往復に使える残量がその分だけ削れる。subagent には対象ファイルの一覧と観点1〜5を渡し、返させるのは乖離候補だけにする。1件につき「ファイル:該当箇所 → 何と何が食い違うか → 根拠になる原文の引用」。要約や所感を返させない。

   親は返ってきた候補の**引用箇所だけを読み直して裏を取る**。subagent の報告をそのまま指摘として user に出さない。読んでいない原文を根拠に裁可を求めることになるため。裏が取れなかった候補は落とす。

   subagent は読むだけで、編集・裁可・索引の更新をしない。それらは親の責務として残す。
2. 非公開側と本リポの両方に実体があるファイルでは、索引の `正本:` が示す向きに照らして乖離を見る。`正本:` が未記入のファイルは、この実行で向きを決めてフェーズ3で書き込む
3. 精読したファイルについて、次の5観点で乖離を洗い出す
   1. docs-agents 内部の相互矛盾（例: `test-policy.md` と `issue-driven-workflow.md` で基準がずれる）
   2. CLAUDE.md（グローバル/リポ別）と docs-agents の乖離（CLAUDE.md にしか書かれていない規則が docs-agents の更新で置き去りになっていないか）
   3. Skill の trigger 記述（`description:`）と本文の乖離（規則が変わったのに Skill の説明が古いまま残っていないか）
   4. モデル世代による陳腐化（アンカーのモデル ID がメジャー世代で変わったときだけ見る）。古いモデルの弱点を補う目的で書かれた記述が、現行モデルでは能力を削ぐ制約になっていないか。徴候は「モデル名やモデル系列で分岐している」「一度に触ってよい範囲を狭めている」「出力の長さ・粒度を一律に縛っている」。**該当しても自動では消さない。** 弱点が本当に消えたのかは実地でしか分からないので、フェーズ2で「まだ必要か」を問う形の指摘として出す
   5. 層1（`settings.json` / `hooks/*.sh`）とガイドの乖離。ガイドが規定する deny の共通項目・フック一覧・attribution が実体に無い、または実体にあるものがガイドに載っていない。**ここは実体が正**なので、提案の向きは常に「ガイドを実体に合わせる」

**5の洗い出しが完了するまで、見つけた乖離を1件ずつ user へ提示・確認しない。**フェーズ1を終えてからフェーズ2でまとめて出す。索引の更新は、フェーズ2の裁可・反映がすべて終わったあとに行う。

## フェーズ2: 統合

1. 乖離ごとに、どちらが正（基準の実体）かを判定する。同じ規則が複数箇所に重複しているだけなら、正本を残し他方を「正本を参照する」形に薄くする方向で提案を組み立てる（内容そのものを複製しない）
2. 指摘一覧をチャットに提示する（ファイルに書き出さない）。各指摘は「対象ファイル:該当箇所 → 矛盾/陳腐化の内容 → 提案」の形で1件ずつ書く
3. 指摘ごとに user の明示的な裁可（YES/NO/修正）を得てから該当ファイルを編集する。**内容そのものへの同意を毎回得る**（複数の指摘をまとめて一括承認する運用にしない）。user は対話で指示してもよいし、ファイルを直接編集してもよい
4. 裁可された指摘のみを反映する。編集は該当箇所の最小差分に留め、裁可を経ていない周辺の言い回しには手を入れない

## フェーズ3: 索引整理

1. 反映後、編集した Skill の frontmatter `description` が本文と再び一致しているかを確認する
2. CLAUDE.md 側の `@import` や docs-agents への参照が、実体のファイル名・見出しと一致しているかを確認する
3. `.claude/RULES.md` を更新する。既存行への上書きであって追記ではない。**今回精読したファイルの行だけ** `棚卸し:` を書き直し、要約・相互参照・`正本:` を現状に合わせる。フェーズ0で「未登録」だった行を作り、「消滅」だった行を消す。読まなかったファイルの行は一切触らない。索引が存在しなかった場合はここで対象節の全ファイル分を新規に書き出す
4. 先頭のアンカー行を `git rev-parse --short HEAD` と当日の日付で書き直す。本 Skill はコミットしないので、ここで記録するのは**今回の修正を含まない HEAD** になる。次回の実行では今回のコミットがコミット範囲に現れるが、3 でハッシュを書き直した行は「変更なし」に落ちるため二重に読まれない
5. user が「差分のまま残す」と裁可した乖離を「裁可済みの差分」節へ1行で追記する。解消済みの行は削除する
6. ずれが残っていればフェーズ2に戻る。無ければ変更ファイル一覧・反映済み指摘の要約・**今回読まなかった対象の件数**を報告して終了する（網羅していないことを user から見えるようにする）

## 定期実行

週次程度の定期起動を想定する。設定そのものは本 Skill の責務外で、user が `schedule` Skill 経由で別途組む。

## 制約

- プロダクトコード（各リポの src/ 等）は書かない
- 裁可を経ていない指摘は反映しない。指摘が複数ある場合、要約や「まとめてOK」だけで済ませず、内容ごとの同意を確認する
- コミット・push はしない。変更はワーキングツリーに残し、user がレビューしてコミットする
- `.claude/RULES.md` は索引であり規則の実体ではない。ポインタ・要約・相互参照・更新日時のみを書き、規則の内容そのものを複製しない
