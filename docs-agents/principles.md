# Principles — AI Agent 運用の設計原則

注意し続ける人間を前提にしない開発体系。導入順に5段で示す。

各段は、本質・それを支える機構・次へ進んでよい条件で構成する。

| 本書が扱う | 本書が扱わない |
|---|---|
| なぜその順序か。各段の本質・機構・完了条件 | 手順・設定値・チェック項目（同ディレクトリの各ガイド） |

---

## 用語

### 三役

| 役 | 担当 |
|---|---|
| **user** | 決裁者。フェーズと保証の裁可、レビュー、マージ、デプロイ |
| **相談者** | 調査・設計・Issue 作成。実装しない。開放チャットで動く |
| **実行者** | Issue に基づく実装とローカルコミット。専用ブランチで動き、リモートに触れない |

### フェーズ

リポが今どちらにあるかを user が決め、CLAUDE.md に明記する。

- **MVP 期** — 方向性・構造が固まっていない立ち上がり期。相談者が直接実装してよい。駆動文書は PLAN.md / JUDGE.md。
- **Issue ドリブン期** — 方向性が固まった段階。三役の分業に従う。駆動文書は保証台帳とテスト。

### 駆動文書

その時期の開発を進行させ、更新され続ける文書。

- **PLAN.md** — MVP の定義・完成条件・作業記録。
- **JUDGE.md** — 実装中の技術選定と判断の記録。
- **台帳**（`docs/guarantees.md`） — 公開面の保証と、対応するテストを対にした一覧。

### 保証まわり

- **保証** — 壊れてはいけない振る舞い。自然言語で書く。
- **保証節** — Issue 内で「新たに宣言する保証」と「維持する保証」を書く節。user が裁可する。

### 分業の緩和3経路

- **リアルタイム ops** — 事前に設計できない障害対応。
- **単発例外** — user が明示的に直接編集を指示した回。
- **軽量経路** — ロジックにも台帳にも触れない小さな差分。

## 通底する前提

**注意し続ける人間を前提にしない。**

規約は読み手の集中力に依存し、集中力は疲れると落ちる。守られるかどうかが人の状態に左右される仕組みは、そもそも作らない。禁止は文書でなく機構に置き、索引は手で書かず生成し、CI はローカル検証と同じものを二重に回す。文書に書いて守らせるのは最後の手段であって、最初の手段ではない。

この前提が最も露骨に出るのがテストの定義で、そこでは「実行者が壊したことに自分で気づくための装置」と規定される（Step 4）。人が注意して見つけるのではなく、壊した本人が提出前に気づく経路を用意する。

---

## 導入順序

1. 作る前に型を決める
2. 禁止を文書でなく仕組みに置く
3. 読まれる場面ごとに知識を置く
4. 守る保証を先に裁可する
5. 決める人と作る人を分ける

順序には依存がある。型が決まらないと何を遮断すべきかが決まらない。遮断が無い状態で知識を増やすと事故の速度だけが上がる。知識の置き場が定まらないと保証を書く土台が無い。そして保証が固まる前に分業すると、実行者が何を壊してはいけないか分からないまま走る。

**最小構成は 1〜3。** この3段は公開の有無にもチーム規模にも関わらず効く。Agent が走るなら必ず要る。4〜5 は、公開物を持つとき、または複数人・複数セッションで並行し始めたときに足す。

## Step 1 — 作る前に型を決める

### 本質

作り始める前に、それがどの型かを決める。以降の規定はすべて型から導かれる。何を遮断するか、何を検証手段にするか、README に何を書くか、どこまでテストするか。型が決まらないと一つも決まらない。

規定の側も、必須項目を固定リストで持たない。型ごとに「下限（必ず満たす観点）」だけを定め、その上の構成は毎回決める。テンプレートを埋める作業ではなく、判定する作業になる。

判定の軸は対象ごとに違う。

| 対象 | 判定軸 |
|---|---|
| リポ | 類型（設定 / ロジック / Web / ツール）× 公開状態 |
| README | 使わせるのか、読ませるのか。読ませるなら証拠はコードか数字か |
| モジュール | 利用者の実行環境に取り込まれるか。取り込まれないなら、渡すのは機械か作法か |
| 図 | 分岐・失敗経路・境界・対比のどれかがあるか |

割れやすい境目にはリトマス試験を置く。「結果の数字を全部消したら価値は残るか」「パラメータを全部外部注入に追い出しても、動く機械として残るか」。判定者によって答えが変わる問いは、判定基準として使えない。

そして最初の判定は常に、やらないという判断を含む。図を描くか。コメントを書くか。Issue にするか。落とすことが最も効く。

### 機構

判定結果は口頭で共有せず、読まれる場所に固定する。リポ類型とそこから決まる検証手段は CLAUDE.md へ。README の種別は README の構成そのものへ。フェーズも CLAUDE.md へ。

フェーズだけは user が決め、相談者は判断も変更もしない。判定を人格の外へ出すことで、その場の都合で揺れなくなる。

### 完了条件

リポ類型・検証手段・フェーズが CLAUDE.md に書かれている。以後の判断を、この記述を参照して行える。

### 参照

[repo-guide.md](repo-guide.md) / [harness-guide.md](harness-guide.md) §1 / [readme-guide.md](readme-guide.md) §1 / [module-guide.md](module-guide.md) §1 / [diagram-guide.md](diagram-guide.md) §1

## Step 2 — 禁止を文書でなく仕組みに置く

### 本質

文書に書いた禁止は守られない。読み手は疲れるし、Agent は長い指示を読み飛ばす。だから禁止は CLAUDE.md ではなく `settings.json` の deny とフックに置く。同じ内容でも、置き場所が違えば守られる確率の桁が違う。

そのうえで、壁を立てるだけなら deny で足りる。フックの利得は、拒否と同時に正しい経路へ寄せられる点にある。Agent は拒否されると別の手を試すので、何を試すかを拒否文で指定できる。**遮断は否定ではなく分岐器である。**

### 機構

deny は文字列の前方一致しか見ない。禁止したい対象が文字列ではなく行為であるときは、PreToolUse フックでコマンドを解釈して判定する。引用符の中身を先に落とし、コマンド位置に限定し、`sudo` / `env` / パス付き実行を吸収する。

拒否メッセージには理由と代替手順の両方を入れる。可能なら、正しい編集先を機械的に組み立てて返す。

attribution を空にするのは、Agent は道具であって共著者ではないという立場から。commit 履歴に人間以外の名前を混ぜると blame の可読性も下がる。

生成と遮断は別の対策であり、両方要る。索引を自動生成しても、書き込み先が違えば索引には現れない。

### 完了条件

deny とフックが置かれ、拒否メッセージが理由と代替手順の両方を返す。CLAUDE.md に禁止事項が一つも書かれていない。

## Step 3 — 読まれる場面ごとに知識を置く

### 本質

何を書くかより、いつ読まれるかで置き場が決まる。そして管轄を重複させない。

### 機構

| 読まれる場面 | 置き場 |
|---|---|
| 毎回効く短い規則 | CLAUDE.md に1行 |
| 「〜するとき」と条件を言えるもの | skill（description が起動条件の宣言になる） |
| 規則から指す共有辞書・ガイド | 独立ディレクトリ。絶対パスで参照 |
| 未整理の思考 | ハーネスの外。自動で読ませない |

skill の description に起動条件を列挙することで、暗黙知が宣言に変わる。移住のトリガーは「またこのドキュメントを手で渡したな」と気づいた瞬間であり、一括移行はしない。

各ガイドは冒頭に管轄表を持ち、他ガイドの領分を書かない。引用したくなったら、それは引用元を直す合図である。

読み手が人間だけでない文書は、見出しを英語・本文を日本語で書く。構造は国際的に読ませ、記述の精度は母語で保つ。英語版を持つ文書では、そこから分離した文書も対で作る。片方だけ本文に畳み込む非対称を残さない。

### 棚卸し

置き場を分けた結果として、規則ファイルは増え続ける。だが規則同士の矛盾を検出する仕組みは規則の中には無い。外から定期的に見る以外にない。

棚卸しは索引を挟み、前回記録より後に変更されたファイルだけを深読みする。索引が無い設計では実行のたびに全対象を読むことになり、コストが対象数に比例して積み上がる。除外リストは保守せず、機械的に切り分けられる基準で対象を決める。指摘は1件ずつ裁可する。

### 完了条件

新しい規則を足すとき、置き場が読み込みの契機から一意に決まる。CLAUDE.md に手順が溜まっていない。棚卸しが定期実行に乗り、索引に前回時点が記録されている。

## Step 4 — 守る保証を先に裁可する

### 本質

テストは変更可能性の担保である。品質を証明するためではなく、安心して変えられる状態を作るために書く。壊したときに気づけないコードは、動いている限り誰も触れなくなる。

そのうえで、テストを書くのは実行者。人間の仕事は保証を裁可することに移る。TDD がテストを先に書く規律なら、GDD（Guarantee-Driven Development）は裁可を先に行う規律である。

テストそのものが正なのではない。裁可された保証を実行可能な形に書き下ろしたものが正。

### 機構

Issue の保証節を user が読み、削る・足す・直したうえで `status: open` にする。open とは裁可済みという意味であり、実行者は `status:` を触らない。テストを伴わない変更は `保証: なし（理由）` と明示する。

台帳には契約面だけを載せ、内部実装のテストは載せない。濃淡はリスクベースで決める。公開 API は厚く、内部実装は薄く、見た目は user の手動検証へ回す。

### 駆動文書の交代

MVP 期の駆動文書は PLAN.md と JUDGE.md である。何を作れば完成かを PLAN.md が、なぜその実装かを JUDGE.md が保持し、Agent はこれを更新しながら実装する。ただしこの2つは足場であって、永続を求めない。公開時に README へ昇華し、**昇華したら削除する**。判断の全文が要るなら `docs/` へ移し、README と原本の二重管理を残さない。経緯は git にある。

台帳が正式運用に上がる瞬間が、駆動文書の交代点である。壊してはいけない振る舞いが台帳に固定された時点で、PLAN.md の役目は終わっている。フェーズ移行とはこの交代のことであり、宣言だけを先に変えても実体は動かない。

### 検証の二重化

裁可された保証は、実行者のローカルと CI の二か所で同じものを回す。CI で新しい検証を足すのではなく、ローカル検証と同一のものを重ねる。目的は網羅ではなく、実行者が回し忘れた場合の取りこぼしを拾うことにある。二か所で内容が食い違えば、片方は必ず信用されなくなる。

ローカル検証だけで足りるリポでは CI を持たない。外から見えるものを持つかどうかで決まる。

### 完了条件

台帳が正式運用に格上げされ、README から到達できる。PLAN.md / JUDGE.md が README と `docs/` へ昇華され、削除されている。この時点でフェーズを Issue ドリブン期へ上げる。台帳の格上げ・駆動文書の廃棄・フェーズ変更は同一イベントとして束ねる。

## Step 5 — 決める人と作る人を分ける

### 本質

三役を分けるのは、決定を実装の都合から守るため。決定と実行を同じ時間の中でやると、決定が実行に引きずられて検証できなくなる。

### 機構

相談者は Issue を書いて止まる。実行者は worktree で実装しローカルコミットで止まり、リモートには一切触れない。user がレビューし、push から PR 作成・マージ・記録までは専用のコマンドが一括で行う。リモートに載るのは、ローカルでレビュー済みのものだけになる。

ローカルの Issue ファイルが唯一の真実で、GitHub Issue は記録用ミラー。問題が出たら元の Issue を再 open せず派生 Issue を立てる。記録を上書きしないため。

デプロイも同じ形で人手を抜く。CI 通過を条件に自動で押し出し、手動オペを挟まない。判断が要るのはマージまでで、そこから先に人が立つ理由は無い。

硬直は3経路で緩める（用語を参照）。常用化したらフェーズ自体を戻す。

### 完了条件

Issue から公開まで、人手の判断が user のレビューと裁可だけに収束している。

### 参照

[issue-driven-workflow.md](issue-driven-workflow.md) / [cicd-guide.md](cicd-guide.md)

## 適用範囲

フェーズ概念が効くのは公開パイプラインに乗るリポだけ。個人インフラ・ops 運用リポには適用せず、直接編集を基本とする。ただし Step 1〜3 は公開の有無に関わらず効く。型の判定・遮断・知識の配置は、走る Agent がいる限り必要になる。
