# Diagram Guide

Mermaid 図の作成ガイド。README・技術記事・解説ドキュメントなど、GitHub 上でレンダリングされる図すべてに適用する。

このガイドの前提は、**GitHub が ```` ```mermaid ```` フェンスを本文カラム幅（約 768px）に縮小して描画する**こと。図を SVG に焼かず、フェンスのままコミットする（テーマ追従と差分閲覧が効かなくなるため）。したがって図の幅はそのまま文字サイズになる。

このガイドの目的は、きれいな図を描くことではない。**その図が無いと伝わらないものだけを、読める大きさで描く**状態を作ることにある。

---

## 0. 描く前に通す順序

```
箇条書きで書いてみる → 足りるなら図は要らない（大半がここで落ちる）
        ↓
主題を決める（分岐 / 境界 / 対比 のどれを見せるか）
        ↓
向きを決める（TD 既定）
        ↓
形と線種に型を割り当てる
        ↓
幅を数える
```

**手順1で落とすことが、このガイドで最も効く判断**である。以降の技法はすべて、描くと決めた図の質を上げるためのものにすぎない。

---

## 1. 描くか、描かないか

**分岐・失敗経路・境界をまたぐグループ化・対比のどれも無いなら、図にしない。**

順番に起きるだけの処理は、番号付きリストの方が速く読める。`A → B → C → D` を図にしても、矢印は「次に起きる」以上の情報を持たない。

図が正当化されるのは次のいずれかを持つときだけ。

| 主題 | 図でしか表せない理由 |
|---|---|
| **分岐** | 条件で処理が割れて、また合流する。文章では分岐の先を読み終えるまで全体が見えない |
| **失敗経路** | リトライループ・複数の終了状態。制御フローは線形の文章に写せない |
| **境界** | デバイス・ネットワーク・信頼境界をまたぐ配置。subgraph でしか表せない |
| **対比** | before / after、あるべき姿と現状。並置そのものが主張になる |

**「全体像」は主題ではない。** 全体像を描こうとすると、必ず分岐の無い一直線か、抽象度の混ざった散らかった図になる。

全体像そのものが要るなら、図ではなく**ディレクトリ構成表かコンポーネント表**で出す。どうしても図にするなら、後述 §5 に従って主題ごとに分割する。

### 描かないときの置換先

図を落とすときは、中身に合った形へ置き換える。「図をやめる」と「情報を捨てる」は別のこと。

| 図の中身 | 置換先 |
|---|---|
| 順番に起きる処理の列挙 | 番号付きリスト |
| 名前と役割・段の対応（スクリプト名 → フェーズ等） | 表 |
| 1ステップだけの変換 | 一文 |

### 主題が潰れていないか

描くと決めたら、**そのリポで一番おもしろい判断が図の中で1ノードに潰れていないか**を確認する。潰れているなら、図の主題が間違っている。

その1ノードを展開したものこそが描くべき図であり、周辺のパイプラインは本文に落とす。

## 2. 幅 — 縦は無料、横は有料

縦に伸びる分はスクロールするだけで、文字の大きさは変わらない。横に伸びた分だけ縮小され、読めなくなる。

| 規則 | 理由 |
|---|---|
| `TD` を既定にする。`LR` はチェーンが4ノード以下のときだけ | `LR` の幅 ∝ チェーン長、`TD` の幅 ∝ 分岐本数。分岐の無い処理列は必ず `TD` の方が狭い |
| エッジラベルは最短にする。API 列挙・引数・条件式を載せない | ノードを増やさず幅だけ増やすため、単位幅あたりの情報量が最も悪い |
| ノードラベルは全角12文字程度まで。詳細は図の下の本文へ | 長いラベルは、そのランク全体の幅を押し広げる |
| 横並びの subgraph は2つまで。3つ以上なら `TD` で縦に積む | subgraph は内容に加えてパディングと枠線ぶんの幅を食う |

しきい値（4ノード / 全角12文字 / subgraph 2つ）は運用で調整してよい。**動かしてはいけないのは「幅が文字サイズである」という前提の方**である。

### 幅の数え方

レンダリングせずに見積もる。**最長ランクのノード数 × その行のラベル長 + エッジラベル長の合計**が幅の目安になる。`LR` なら最長ランク＝チェーン全体、`TD` なら最長ランク＝最も広い分岐の段。

削る順序は、**エッジラベル → ノードラベル → 向きの変更 → 図の分割**。

## 3. 形と線種に情報を載せる

ノードの形と線の種類は、**幅をまったく増やさずに情報の次元を1つ増やす**。全ノードが同じ四角・全エッジが同じ矢印の図は、この余地を捨てている。

### ノード形状

| 記法 | 型 |
|---|---|
| `([ ])` | アクター（人・外部の呼び出し元） |
| `{{ }}` | サービス・変換器 |
| `[( )]` | データストア |
| `{ }` | 判断・分岐点 |
| `[/ /]` | 外部からの投入・ファイル |
| `[ ]` | それ以外の処理 |

### 線種

| 記法 | 意味 |
|---|---|
| `-->` 実線 | ローカル・同一プロセス内 |
| `-.->` 点線 | ネットワーク越し・非同期 |
| `==>` 太線 | 人間の物理操作・主経路 |

割り当ては固定ではないが、**1つの図の中では必ず一貫させる**。一貫していない使い分けは、情報を載せるどころかノイズになる。

絵文字は幅ゼロの視認アンカーとして使える。アクターや外部サービスなど、**種類が変わる点にだけ**置く。

### 記法

- 改行は `\n` ではなく `<br/>`（新しい Mermaid で `\n` の扱いが変わっている）
- ラベルに記号を含むときは `["..."]` で引用する

---

## 4. 抽象度を混ぜない

1つの図の中でノードが指すものの階層を揃える。**概念（ルート・フェーズ・レイヤー）と実体（プロセス・ファイル・サービス）を同じ平面に置かない。**

混ざる典型は、subgraph に「ルートA / ルートB」のような概念名を付けたうえで、その外側に具体的なミドルウェアやファイルを並べる形。この場合 subgraph を捨て、**構造そのもの（合流・分岐）に語らせる**方が狭く読みやすくなる。

---

## 5. 図を分けるか、まとめるか

**1図＝1主題。** 分けるかどうかは主題の数で決まり、図の大きさでは決まらない。大きすぎるから割る、小さいから足す、はどちらも判断を誤らせる。

分けてよい軸は次の3つに限る。これ以外の理由で分かれている図は、たいてい主題が曖昧なまま増えたもの。

| 軸 | 例 |
|---|---|
| **時間** | ビルド時 / 実行時、セットアップ / 定常運用 |
| **正常系 / 異常系** | 主経路 / 停止・リトライ・強制終了の経路 |
| **before / after** | 移行前の構造 / 移行後の構造 |

### まとめる前に確認すること

**片方が単独で主題を持つかを先に見る。** 持たない図は、まとめる対象ではなく**消す対象**である。主題の無い図をもう1枚に吸収させると、吸収した側の主題まで薄まる。

### 分けたときの規則

- 各図に**主題を示す見出しか一文**を付ける。同じ見出しの下に無説明で2枚並べない（どちらが何なのか読者に判別できない）
- 図をまたいで同じノードを描くときは、ラベルを完全に一致させる
- 分割の軸自体を本文で明示する（「以下は正常系。停止経路は次の図」）
