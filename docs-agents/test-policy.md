# テスト方針

テストは変更可能性の担保である。実行者（AI）が壊したことに自分で気づくための装置であり、注意し続ける人間を前提にしない。

保証（何が壊れてはいけないか）は Issue の保証節で人間が裁可し、テストの実装は実行者が書く。この分業を **Guarantee-Driven Development (GDD)** と呼ぶ。テストそのものが正なのではなく、裁可された保証を実行可能な形に書き下ろしたものである。TDD がテストを先に書く規律だとすれば、GDD は約束の裁可を先に行う規律であり、人間の仕事はテストを書くことから約束を裁可することへ移る。Issueドリブン期のリポはこの方式で保守する（フェーズは各リポの CLAUDE.md で宣言する）。

濃淡はリスクベースで決める: 公開API・契約面は厚く、内部実装は薄く、UI・見た目は user の手動検証に回す。

fix には回帰テストを同梱する。

外部依存は DI で受け、テストは fake で差し替える（実サービスに接続しない）。

各リポは公開面の保証を `docs/guarantees.md`（保証台帳）として持てる。

- **構成**: 自然言語の保証の箇条書き＋対応テスト（ファイル・テスト名）の表。載せるのは契約面の保証のみで、内部実装のテストは載せない。地位は design-decisions.md と同格で、実装と食い違う場合は指摘対象になる。
- **敷設**: 初版は `guarantee-audit` skill で敷く。新規リポは公開パイプラインの第2ステップとして（README が台帳へリンクするため README 作成より先に）、既存リポは既存テストの棚卸しとして。
- **追従**: 以後は Issue の保証節と同一 PR で更新する。台帳とテストの乖離は `guarantee-audit` による定期棚卸しで検出する。
- **スコープ**: 台帳のスコープ外に新しい契約面が生まれたときは、スコープに入れるかを Issue 起草時に判断する（対象外の記載は素通りの根拠にしない）。
- **到達性**: 台帳は README から到達可能にする（リンク位置は readme-guide の規定に従う）。
- **Gaps 節**: 保証すべきだがテストが無いものを見送り理由ごと記録し、空になったら節ごと削除する。

台帳は各リポの `docs/guarantees.md` が正本であり、この配置は変えない。ただし複数リポを並行して回すと、「今フリート全体で何を約束しているか」を一望できる場所が無くなる。裁可する側が全体を見渡せないのは台帳の目的に反するため、rebuild のたびに走査対象を見て台帳の symlink を1箇所へ集約する運用を敷いている。実体はコピーせず、正本は各リポに残ったまま参照だけを束ねる。同名リポが複数の走査対象にある場合は優先順位で解決し、下位には走査元の接頭辞を付ける（手順は `apps/lpt/README.md` を参照）。
