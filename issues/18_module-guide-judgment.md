### 背景

`docs-agents/` の7ガイドは2層に分かれる（Issue 17 参照）。`module-guide.md` は「リポを作るたびに毎回フルコストで発生し、答えがリポごとに違うためテンプレート化できない」判断層に属する。

判断層のもう1本 `readme-guide.md` は269行あり、§1 にリトマス試験（使わせる？→ Type B。読ませるなら証拠がコードか数字かで Type A / Type C）という**判定手順**を持つ。`repo-readme` Skill はこれを起点に種別を確定してから書き始める。

`module-guide.md` は43行で、型の表（組み込み型 / ツールキット型 / 研究型）はあるが、**目の前のリポがどれなのかを決める手順が無い**。多数のリポを並行して立ち上げる運用では、この判定が毎回発生する。手順が無ければ判定はその場限りになり、リポ間で基準がぶれる。

### 1. 型の判定手順を §1 の冒頭に足す

現在の §1 は「正体を『汎用部分 + 固有部分』に分離して一文で定義する」から始まり、いきなり3型の表に入る。表の前に判定手順を置く。

`readme-guide.md` §1 のリトマス試験と同じ形式（分岐する問いの連鎖）で書くこと。判定の分かれ目として少なくとも次を扱う。

- 汎用部分が**利用者のビルド・実行環境に取り込まれる**か、それとも利用者が読んで自分の文脈に写すか（組み込み型か、それ以外か）
- 後者のうち、リポが提示するのが**再利用できる機械**か、**問いと検証の作法**か（ツールキット型か研究型か）
- 判定が割れる場合にどちらへ倒すか、およびその根拠

**表の内容は変えない。** 3型の定義・配布形態は既存のまま維持し、そこへ至る手順だけを足す。

#### readme-guide.md の Type A/B/C との関係を明記する

現状、本リポには2つの型の分類が併存している。

- `readme-guide.md` §1 の Type A / B / C（README の書き方を決める分類）
- `module-guide.md` §1 の組み込み型 / ツールキット型 / 研究型（設計と配布形態を決める分類）

名前も粒度も違うが、どちらも「このリポは何か」を問うており、**読み手は同じ質問に2回答えているように見える**。実際には目的が違う（前者は読者に何を見せるか、後者は何をどう配るか）。

両者の対応関係を1段落で明記する。含めること。

- 2つの分類は独立して立てるものではなく、片方が決まればもう片方はおおむね決まること（対応の実態を書く。機械的な1対1対応を無理に作らない）
- どちらを先に決めるか。`repo-standardize` が `readme-guide` §1・§3 を先に使い、`module-dev` は設計段階で走ることを踏まえて順序を示す
- 食い違った場合にどちらを優先するか

`readme-guide.md` 側には手を入れない（対象ファイルに含めない）。参照は片方向にする。

### 2. モジュール境界の切り方を §2 に足す

§2 は「汎用部分はドメイン語彙なし」「外部依存は注入」「一方向依存」という**守るべき性質**を述べているが、目の前のコードをどこで切るかの指針が無い。境界の判断を助ける記述を足す。

扱うこと。

- 何が「ドメイン語彙」にあたるかの見分け方。変数名・型名・設定キーのどこに現れるか、判断に迷う具体例（業界固有の用語か、一般的な語彙か）
- 汎用側に置くか固有側に置くか迷ったときの既定の倒し方。**迷ったら固有側**（汎用側に置いたものは後で剥がすコストが高く、固有側にあるものを汎用へ引き上げるのは安い）という非対称性を明示する
- モジュールを分けるべき/分けないべきの目安。1つしか実装が無い抽象を先に作らないこと

### 3. 既存リポへのモジュール追加を扱う

`module-dev` Skill の description は「新しいモジュールリポを始めるとき、**既存リポにモジュールを追加するとき**、配布形態やデモ方式を決めるとき」を対象に挙げているが、ガイド本体は新規リポの型決めしか扱っていない。既存リポへ足す場合の判断を短い節として足す。

扱うこと。

- 既存リポにモジュールとして足すか、新しいリポを立てるかの分かれ目
- 既に型が決まっているリポへ、その型に合わないモジュールを足したくなった場合の扱い

**節を厚くしすぎない。** 判断の分かれ目を示すことが目的で、手順書にはしない。

### 全体の分量について

現在43行。目安として100〜150行程度を想定するが、行数を目標にしない。**判断の分かれ目を示す記述だけを足し、既に自明なことや他ガイドの管轄を書かない。**

特に次を書かないこと。

- 具体的なディレクトリ名・コマンド・設定例（構造は §2 の既存のツリーで足りる）
